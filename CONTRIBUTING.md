# CONTRIBUTING

> **Guidelines for contributing to the WaysNX Business Framework (WBF).**

---

# Welcome

Thank you for your interest in contributing to the **WaysNX Business Framework (WBF)**.

WBF is an open engineering framework focused on software architecture, business analysis, engineering standards, documentation, and enterprise software development.

Every contribution—whether it is documentation, architecture guidance, templates, examples, or tooling—helps improve the framework for the wider engineering community.

We welcome contributions from:

- Software Architects
- Enterprise Architects
- Solution Architects
- Developers
- Technical Writers
- Business Analysts
- QA Engineers
- DevOps Engineers
- Students
- Technology Enthusiasts

---

# Purpose

This document explains how to contribute to the framework while maintaining:

- High documentation quality
- Architectural consistency
- Engineering best practices
- Repository organization
- Long-term maintainability

Following these guidelines helps ensure that contributions are easy to review, understand, and integrate.

# Contribution Principles

All contributions should follow these principles.

## Quality First

Prioritize quality over quantity.

A small, well-written improvement is more valuable than a large but inconsistent contribution.

---

## Documentation Driven

Documentation is considered a primary engineering asset.

Whenever appropriate:

- Explain the reasoning.
- Provide examples.
- Update related documents.
- Maintain cross-references.

---

## Consistency

Maintain consistency across:

- Terminology
- Formatting
- Naming conventions
- Diagrams
- Tables
- Document structure
- Markdown style

---

## Simplicity

Keep contributions clear and easy to understand.

Avoid unnecessary complexity.

---

## Reusability

Design templates, specifications, and examples so they can be reused across multiple domains and technologies.

---

## Technology Independence

Whenever possible, contributions should remain independent of specific programming languages, frameworks, or vendors.

The framework should remain broadly applicable.

# Reporting Issues

If you discover a problem, please create an issue describing:

- The problem
- Steps to reproduce
- Expected behavior
- Actual behavior
- Possible solution (optional)
- Related documents

Include screenshots when appropriate.

Well-written issue reports significantly improve review efficiency.

---

# Suggesting Enhancements

Enhancement requests should clearly describe:

- Current limitation
- Proposed improvement
- Benefits
- Possible alternatives
- Expected impact

Feature requests should focus on improving the overall framework rather than individual implementation technologies.

# Contribution Workflow

All contributions should follow a structured workflow.

```text
Idea
   │
   ▼
Issue / Discussion
   │
   ▼
Implementation
   │
   ▼
Self Review
   │
   ▼
Pull Request
   │
   ▼
Peer Review
   │
   ▼
Approval
   │
   ▼
Merge
```

This workflow helps maintain framework quality and transparency.

---

# Creating a Pull Request

Before submitting a Pull Request:

- Ensure your changes are complete.
- Verify Markdown formatting.
- Check spelling and grammar.
- Update related documentation.
- Remove unnecessary files.
- Verify links.
- Update diagrams if necessary.
- Ensure examples are correct.

A high-quality Pull Request reduces review effort.

---

# Pull Request Checklist

Before submitting, verify:

- Documentation builds correctly
- Markdown formatting is valid
- Links work correctly
- Images render correctly
- Tables are aligned
- Terminology is consistent
- Related documents are updated
- Cross references are accurate
- No duplicate information exists
- Examples have been validated

---

# Documentation Standards

Documentation should:

- Use clear headings
- Use concise language
- Follow repository formatting
- Use Markdown best practices
- Include diagrams where helpful
- Include examples where appropriate
- Avoid unnecessary repetition

Documentation should prioritize readability.

---

# Commit Messages

Write meaningful commit messages.

Recommended format:

```text
type(scope): concise description
```

Examples:

```text
docs(governance): improve governance workflow

docs(specifications): add architecture template

docs(repository): update navigation guide

fix(markdown): correct broken links
```

Keep commit messages concise and descriptive.

---

# Branch Strategy

Recommended workflow:

```text
main
 ├── feature/*
 ├── docs/*
 ├── fix/*
 └── release/*
```

Use descriptive branch names.

Examples:

```text
feature/domain-model

docs/governance-update

fix/navigation-links
```

Review feedback should remain respectful and constructive.
